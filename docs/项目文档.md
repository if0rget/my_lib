# 图书管理系统 项目文档

> 定位：学习 Go 的练手项目。后端 Go，前端 React；开发时前后端分开跑，部署时合成一个服务。
> 选型原则：**前端尽量省事，部署尽量简单**，把精力留给 Go。
> 说明：Go、React、PostgreSQL、要有数据库迁移、要容易部署是已定的要求；其余选型和功能范围是默认建议，可以随意改。

## 1. 技术选型

### 1.1 后端

| 用途 | 选型 | 为什么选它 | 备选 |
|---|---|---|---|
| 语言 | Go 最新稳定版 | 本机还没装 Go，直接装最新的 | — |
| Web 框架 | **Gin** | 资料多、上手快，路由 / 中间件 / 参数绑定一套齐全 | 标准库 `net/http`（更能练基本功，但要自己搭的东西多）、Echo、Fiber |
| 数据库 | **PostgreSQL 17** | 你指定；功能强、标准 SQL 支持好，Go 社区用得很多 | MySQL、SQLite |
| 数据访问 | **GORM**（驱动 `gorm.io/driver/postgres`，底层是 `pgx`） | 和 Gin 是事实上的标配，上手快 | `sqlx` / `sqlc`（手写 SQL，更清楚底层发生了什么） |
| 参数校验 | Gin 自带的 binding（`go-playground/validator`） | 不用额外引入 | — |
| 登录鉴权 | **JWT**（`golang-jwt/jwt/v5`）+ `bcrypt` 存密码 | 前后端分离的常规做法，正好练中间件 | Session + Cookie |
| 配置 | 环境变量 + `godotenv` | 够用且简单 | Viper（项目大了再换） |
| 日志 | 标准库 `log/slog` | 官方结构化日志，不用第三方 | Zap |
| 数据库迁移 | **golang-migrate** | 表结构用带版本号的 SQL 文件管理（每次变更一对 `up` / `down`），可回滚、可追溯；不用 GORM 的 `AutoMigrate` | `goose`（用法类似，更轻）、Atlas（按模型自动生成迁移） |
| 测试 | 标准库 `testing` + `httptest` + `testify` | Go 测试的常规组合 | — |
| 接口文档 | `swaggo/swag`（可选） | 注释生成 Swagger 页面，方便前端联调 | 手写 Markdown |
| 热重载 | `air` | 改代码自动重启 | — |

### 1.2 前端

| 用途 | 选型 | 为什么选它 |
|---|---|---|
| 框架 | **React 19 + TypeScript** | 你指定了 React；TS 能让接口字段对不上时直接报错 |
| 构建 | **Vite** | 现在的默认选择，启动快，配置少 |
| UI 组件 | **Ant Design 5** | 表格、表单、弹窗、分页现成，后台管理类页面基本拼出来就行，中文文档 |
| 路由 | React Router | 最通用 |
| 请求与缓存 | **TanStack Query** + `axios` | 列表加载、刷新、loading 状态都不用自己写 |
| 登录状态 | Zustand | 只存 token 和当前用户，很轻 |

### 1.3 开发环境

- **Docker Compose** 起 PostgreSQL，不污染本机（WSL2 下需装 Docker Desktop 并开启 WSL 集成）。
- 本机 Node 已是 v22，够用；包管理用 `pnpm` 或 `npm` 均可。
- 开发时 Vite 把 `/api` 代理到后端，避免跨域问题。
- `Makefile` 放常用命令（启动、测试、格式化、`migrate-up` / `migrate-down` / 新建迁移文件）。

### 1.4 部署

目标：**一台装了 Docker 的机器上，一条 `docker compose up -d` 就能跑起来。**

| 做法 | 说明 |
|---|---|
| 前端打进后端 | `vite build` 的产物输出到 `server/internal/web/dist`（`embed` 只能嵌入本模块目录内的文件），再用 Go 的 `embed` 嵌进二进制，由 Gin 直接提供静态页面。线上只有一个服务、一个端口，不需要 Nginx，也没有跨域 |
| 单个静态二进制 | `CGO_ENABLED=0` 编译，不依赖系统库；`pgx` 是纯 Go 驱动，正好满足 |
| 多阶段 Dockerfile | 第一阶段构建前端，第二阶段编译 Go，最后拷进 `distroless` / `alpine` 小镜像（几十 MB） |
| 启动时自动迁移 | 迁移 SQL 同样用 `embed` 打进二进制，服务启动时调用 golang-migrate 自动升到最新版本，部署时不用手动建表 |
| 配置全走环境变量 | 数据库地址、JWT 密钥、端口都从环境变量读，镜像本身不含任何配置 |
| 生产用 compose 文件 | `docker-compose.prod.yml` 里只有 `app` 和 `postgres` 两个服务，数据库挂 volume 持久化 |
| 健康检查与优雅关闭 | 提供 `/healthz`；收到停止信号后等正在处理的请求结束再退出 |

不用 Docker 也行：把编译出的单个二进制拷到服务器，配好环境变量直接运行即可（数据库另装）。

## 2. 功能范围

两种角色：**管理员**、**读者**。

| 模块 | 功能 | 谁能用 |
|---|---|---|
| 账号 | 注册、登录、查看个人信息 | 所有人 |
| 图书 | 列表（分页、按书名 / 作者 / ISBN 搜索、按分类筛选）、详情 | 所有登录用户 |
| 图书管理 | 新增、编辑、删除、调整库存 | 管理员 |
| 分类管理 | 增删改查 | 管理员 |
| 借阅 | 借书、还书、查看自己的借阅记录 | 读者 |
| 借阅管理 | 查看全部借阅记录、逾期列表 | 管理员 |
| 用户管理 | 用户列表、禁用账号 | 管理员 |

**先不做**：预约排队、罚金、图书封面上传、邮件提醒、多馆 / 多副本管理、HTTPS 与域名、CI/CD 自动发布。

## 3. 数据模型

```
users           id, username(唯一), password_hash, role(admin/reader), status, created_at
categories      id, name(唯一), created_at
books           id, title, author, isbn(唯一), category_id, publisher, published_year,
                total_stock, available_stock, created_at, updated_at, deleted_at(软删除)
borrow_records  id, user_id, book_id, borrowed_at, due_at, returned_at(未还为空), created_at
```

业务规则：

- 借书：`available_stock > 0` 才能借，借出后减 1；还书加 1。**扣库存和写借阅记录必须在同一个事务里**（这是本项目最值得练的一个点，顺便可以了解并发下的超借问题）。
- 同一读者同一本书未归还时不能再借；每人同时最多借 5 本；借期 30 天。
- 有未还记录的图书不能删除。
- 首个管理员：服务启动时若库里没有管理员，就用环境变量 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 创建一个；注册接口只能注册读者。

## 4. 接口设计

统一前缀 `/api/v1`，统一返回：

```json
{ "code": 0, "message": "ok", "data": {} }
```

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/auth/register` | 注册 | 公开 |
| POST | `/auth/login` | 登录，返回 token | 公开 |
| GET | `/me` | 当前用户信息 | 登录 |
| GET | `/books` | 图书列表 `?page=&page_size=&keyword=&category_id=` | 登录 |
| GET | `/books/:id` | 图书详情 | 登录 |
| POST | `/books` | 新增图书 | 管理员 |
| PUT | `/books/:id` | 编辑图书 | 管理员 |
| DELETE | `/books/:id` | 删除图书 | 管理员 |
| GET | `/categories` | 分类列表 | 登录 |
| POST / PUT / DELETE | `/categories[/:id]` | 分类增改删 | 管理员 |
| POST | `/borrows` | 借书 `{ book_id }` | 读者 |
| POST | `/borrows/:id/return` | 还书 | 读者（本人）/ 管理员 |
| GET | `/me/borrows` | 我的借阅记录 | 读者 |
| GET | `/borrows` | 全部借阅记录 `?status=borrowed/returned/overdue` | 管理员 |
| GET | `/users` | 用户列表 | 管理员 |
| PATCH | `/users/:id/status` | 启用 / 禁用 | 管理员 |
| GET | `/healthz` | 健康检查（不带 `/api/v1` 前缀） | 公开 |

## 5. 目录结构

```
my_lib/
├── server/                    # Go 后端
│   ├── cmd/server/main.go     # 入口：读配置、连库、注册路由、启动
│   ├── internal/
│   │   ├── config/            # 配置读取
│   │   ├── model/             # GORM 模型（只做映射，不负责建表）
│   │   ├── repository/        # 数据访问：只管查库
│   │   ├── service/           # 业务逻辑：借还规则、事务
│   │   ├── handler/           # HTTP 层：解析参数、调 service、返回 JSON
│   │   ├── middleware/        # JWT 鉴权、角色校验、日志、错误恢复
│   │   ├── router/            # 路由注册
│   │   └── web/               # embed 前端构建产物（dist/ 不入库）
│   ├── pkg/response/          # 统一返回格式、错误码
│   ├── migrations/            # 迁移文件：000001_create_users.up.sql / .down.sql ...
│   ├── go.mod
│   └── .env.example
├── web/                       # React 前端
│   └── src/
│       ├── api/               # 接口请求封装
│       ├── pages/             # 登录、图书、分类、借阅、用户
│       ├── components/
│       ├── store/             # 登录状态
│       └── router/
├── Dockerfile                 # 多阶段构建：前端 + 后端 → 一个镜像
├── docker-compose.yml         # 开发用：只起 PostgreSQL
├── docker-compose.prod.yml    # 部署用：app + PostgreSQL
├── Makefile
└── docs/
```

后端分三层 `handler → service → repository`，请求从上往下走，每层只调下一层。这是 Go Web 项目最常见的组织方式。

## 6. 前端页面

- 登录 / 注册
- 图书列表（搜索、筛选、分页；读者看到"借阅"按钮，管理员看到"新增 / 编辑 / 删除"）
- 我的借阅（读者）
- 分类管理、借阅管理、用户管理（管理员，侧边栏按角色显示）

## 7. 建议的学习顺序

| 阶段 | 做什么 | 练到的 Go 知识 |
|---|---|---|
| 1 | 装 Go，`go mod init`，用 Gin 写一个 `/ping` | 模块、包、基本语法 |
| 2 | 图书增删改查，数据先放内存（slice / map） | struct、方法、JSON 标签、路由、参数绑定 |
| 3 | 接入 PostgreSQL + GORM，用迁移文件建表，拆成三层 | SQL 建表与迁移、interface、error 处理、依赖注入、`context` |
| 4 | 注册登录、JWT 中间件、角色权限 | 中间件、闭包、密码哈希 |
| 5 | 分类、借阅还书（含事务） | 事务、并发问题、业务错误设计 |
| 6 | 给 service 和 handler 写测试 | 表驱动测试、`httptest`、mock |
| 7 | 搭前端，逐页对接接口 | 前后端联调、跨域 |
| 8 | 前端 `embed` 进后端、多阶段 Dockerfile、启动时自动迁移、优雅关闭，用 compose 整体跑起来 | `embed`、交叉编译、信号处理、容器化 |
| 9（可选） | Swagger 文档 | — |

建议每个阶段都先让后端能用 `curl` 或 Postman 跑通，再碰前端。
